What I do

I’m Flushwhy, a software engineer and the founder of FlushLabs. My work sits at the intersection of systems engineering, developer tooling, game technology, and applied research.

I like building software where implementation details matter: tools that make projects easier to ship, native integrations that fit their host applications, and real-time systems that have to respect the limits of their hardware.

FlushLabs is the home for that work. It brings together open-source projects, independent product development, and technical experiments. It isn’t tied to a single framework or product category; the common thread is practical engineering and a preference for software that stays understandable.

Background

My engineering perspective was shaped in part by high-performance computing (HPC). Working around performance-sensitive systems taught me to think beyond source code and consider memory behavior, data movement, concurrency, and the hardware underneath an application.

That experience also shaped how I approach technical communication and review: explain the trade-offs clearly, make assumptions visible, and make the reasoning understandable even when the implementation is specialized.

I work across low-level and application-facing software. My current toolkit includes C and C++, Odin, Go, Python, and Lua, with Unreal Engine and Godot as important parts of my game-development work.

What I’m building

Developer tools and infrastructure

I created Fe to make the path from a project directory to a reproducible, distributable release less fragmented. It brings common setup, build, and release tasks into a consistent CLI while keeping the underlying systems visible.

Game technology

My game-engine work focuses on native integrations and practical runtime systems. The GameJolt Unreal plugin is an example: a C++ integration designed around Unreal’s own architecture rather than a generic wrapper.

I’m also interested in the performance details that shape game experiences: networking, compact data formats, simulation, and predictable frame-time behavior.

Applied AI and simulation

I explore ways to make machine learning useful under real application constraints. That includes local inference, embedded hardware, and ML-assisted physics experiments where model cost, determinism, and runtime behavior matter as much as model accuracy.

Product engineering

Not all of my work is low-level. Projects such as VideoForge and Playriter involve the full product problem: designing workflows, making rendering or document handling reliable, and turning a technical idea into software someone can use.

Engineering principles

  • Understand the machine. Memory, bandwidth, scheduling, and latency are part of the design.
  • Keep the system legible. Prefer direct solutions and intentional dependencies over abstraction for its own sake.
  • Measure real behavior. Benchmarks and reproducible tests should inform optimization.
  • Respect the user. Reliability, clear errors, and predictable workflows are engineering requirements.
  • Build for use. Research matters most when its results can survive contact with a real application.

Good engineering is not complexity for its own sake. It is choosing the simplest design that meets the real constraints, then proving that it works.

Beyond the current projects

I’m also exploring broader systems work, including a FreeBSD-based desktop distribution that builds on the upstream operating system rather than maintaining a separate kernel fork. These experiments are part of the same interest in understanding and improving the complete software experience.
